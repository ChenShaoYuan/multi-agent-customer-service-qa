# 评分解析与容错

## 校验顺序

1. 接受Pydantic对象、字典、JSON字符串或完整json代码块；`json.loads`解析，不执行字符串。
2. 维度须正确，每个子项恰好一次，不允许模型额外总分字段。
3. `parse_score()` 接受整数或完整 `X/N`，正则 `fullmatch`、分母和范围全部校验；拒绝布尔、浮点、负数、越界和附加文字。
4. SP、CM只能0或5；PS-03固定10；PS-01/02扣分须等于所引用业务条款分值之和，最低0。
5. 条款不得缺失、重复、跨类别/子项；程序从规则源附加正文。
6. 有分数的项必须有证据，消息ID须存在、quote须为对应消息连续原文。
7. CM-03须与90秒接入判断一致；CM-04无超时时不能扣时效分，超时免责需模型结合解释判断。
8. 程序相加有效子项，不采信模型自行汇总的总分。

## 区分不同结果

| 场景 | 状态 | raw_score | fallback_score | 处理 |
| --- | --- | --- | --- | --- |
| 真实业务扣为0 | completed | 0或子项之和 | null | 正常评分 |
| 资料缺失 | partial | null | null | 保留可评子项，人工复核 |
| 模型/解析重试耗尽 | technical_error | null | 0 | 技术兜底，人工复核 |
| 未知父标签 | manual_review | null | null | 不调用专业模型 |

原始任务的“兜底0分”和第一周“不把技术故障当业务0分”的边界通过独立 `fallback_score` 兼容。未来总分必须忽略技术兜底并保持复核状态。

两个时效项缺资料时，沟通可能 `evaluated_score=15/evaluated_max_score=15/max_score=25/score_text=N/A`；这既不是15/25，也不是25/25，不能换算成完整维度分。

## 重试和信息边界

默认最多2次尝试，SDK重试关闭；没有指数退避或专门纠错Prompt。`LLM_TIMEOUT_SECONDS` 默认30、范围(0,120]，是请求超时设置，不是整图截止时间。

异常只记录类型、次数和固定描述，不保存可能包含密钥或请求的异常原文。最终报告本身有对话证据，不是全面脱敏的日志；`trace`只有摘要，目前没有持久日志服务。

本周补充了重复/空白消息ID、非字符串内容、倒序时间、混合时区和未获回复用户消息的保护。历史comments按奇偶行推断角色仅用于兼容，不能证明生产数据的真实身份。
